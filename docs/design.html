Agent Warden

A zero-trust enforcement layer for AI agent tool calls — with post-quantum signed receipts that prove what an agent did, for whom, and why it was allowed.

Status: design phase, no code yet · 2026-09-14 · Source: docs/design.md, docs/threat-model.md, docs/decisions/
Why this exists

Agent audit logs today are, at best, HMAC-signed JSON. That proves nothing to anyone who doesn't hold the shared secret, and says nothing about whether entries were deleted. When an agent moves money or touches customer data, the record of what it did is evidence — and evidence needs integrity, origin, completeness, and a lifetime longer than classical signatures may last.

Design1. The idea in one paragraph

An agent proposes a tool call. Warden decides whether it happens, performs it with credentials the agent never sees, inspects what comes back, and — before and after — writes receipts. Each receipt is signed with a hybrid post-quantum signature and linked to the one before it. Periodically, Warden publishes a signed checkpoint to somewhere it doesn't control. Anyone with the public key and a checkpoint can run warden-verify and know that the record is authentic, in order, and complete up to that checkpoint.

3. The life of one tool call

agent ──propose(call)──► Gateway
                           │ 1. identify   task credential → (agent, principal, task)
                           │ 2. pin        tool manifest digest matches registry?
                           │    check      args fit the pinned input schema? (ADR-0013)
                           │ 3. decide     policy(principal, agent, tool, args, taint)
                           │ 4. RECEIPT    type=decision   ◄── durably written before anything runs
                           │ 5. approve    if require_approval: wait for approval receipt
                           │ 6. execute    broker injects tool credential, calls tool
                           │ 7. inspect    tag result with taint source, flag instructions
                           │ 8. RECEIPT    type=result
agent ◄──result (tagged)───┘
Write-ahead rule (ADR-0004)

Step 4 must succeed before step 6 may start. If the log is unavailable, the call is refused.

Implemented in internal/gateway passing as Call, Pending, Approve, and Resume. A rejected credential or unreachable tool server returns an error with no receipt. Unpinned or changed tools are denied (tool_unpinned, tool_changed), as are arguments that don't fit the pinned input schema (invalid_arguments, ADR-0013) and arguments policy can't evaluate (invalid_input), and nothing runs. Approved calls run only via Resume with a matching credential before the approval expires, and the manifest is re-checked just before execution. A result receipt that can't be written withholds the result. go run ./cmd/warden-demo runs a 13-step scenario and writes a log for warden-verify.

4. The receipt

4.1 Payload

Receipts are JSON, canonicalized with RFC 8785 (JCS) before hashing and signing, so the same receipt always produces the same bytes.

{
  "v": 1,
  "domain": "agent-warden/receipt/v1",
  "chain_id": "01J9Z3…",
  "seq": 1042,
  "prev": "sha256:9f2c…",
  "ts": "2026-09-14T15:04:05.123Z",
  "type": "decision",
  "task_id": "01J9Z4…",
  "actor": { "agent": "cert-sha256:ab12…", "principal": "alice@tenant-a" },
  "call": {
    "tool": "payments.refund",
    "manifest": "sha256:77e1…",
    "args_commitment": "sha256:c0ff…"
  },
  "decision": {
    "result": "require_approval",
    "policy_revision": "sha256:4d5e…",
    "rule": "refund_over_limit",
    "taint": ["web:example.org"]
  }
}
FieldPurposeThreat
domain, chain_id, task_idPrevent splicing a receipt into another chain or contextW14
seq, prevOrdering and linkage; prev is the SHA-256 of the previous signed receiptW9
actorWho acted and for whomW4
manifestWhich exact tool definition was calledW5
args_commitment / result_commitmentSalted digests, never raw dataW13
policy_revision, ruleWhy it was allowed — reproducible against that policy versionW2
taintWhich untrusted sources were in contextW1
kid (protected header, not the payload)Which signing key epoch; resolves to a certificateW11

Receipt types: decision, approval, result, key_rotation, checkpoint. Implemented in internal/receipt: decision and result passing. approval (ADR-0009) is implemented too. key_rotation and checkpoint are reserved; until implemented, receipts of those types are refused rather than accepted. Checkpoints (§4.4) turned out not to need a receipt type: they are separate signed statements, kept outside the log.

A result receipt carries the same task_id, actor, and call as its decision, plus result: {decision_seq, status, result_commitment, taint}. decision_seq must be lower than the receipt's own seq; result_commitment is required when status is ok.

Format rules (enforced on sign and verify)

Integers only; seq is at most 253 − 1, the largest integer JCS keeps exact. ts has exactly one spelling: UTC with milliseconds. Digests are sha256: plus 64 lowercase hex characters.

Strict decoding: a payload, header, or log line is accepted only if it is valid UTF-8, already canonical, and decoding then re-encoding it reproduces the exact bytes. This rejects unknown or missing fields, duplicate keys, empty arrays written instead of omitted, and numbers JCS would change. The JCS library used silently rounds integers above 253 and passes invalid UTF-8 through, so these checks are Warden's, not the library's.

4.2 Commitments (ADR-0005)

args_commitment = SHA-256(salt ‖ JCS(args)) with a fresh 32-byte random salt per call. The raw arguments and salt go to a separate, access-controlled store. To prove what one call contained, disclose that call's args and salt; the verifier recomputes the commitment. Salting prevents guessing low-entropy arguments ("was the amount $500?") from the receipt alone.

4.3 Signature (ADR-0002)

  • Algorithm: composite ML-DSA-65-Ed25519 as defined in draft-ietf-jose-pq-composite-sigs-04 (JOSE alg ML-DSA-65-Ed25519; COSE value requested as -58).
  • Construction (per the draft): prehash the message with SHA-512; build the message representative from the prefix, the algorithm label, a 0x00 byte, and the prehash; sign that representative with both ML-DSA-65 and Ed25519; concatenate the two signatures.
  • Envelope: flattened JWS JSON serialization, {"payload", "protected", "signature"}, base64url without padding. The protected header is exactly alg, alg_ref, crit: ["alg_ref"], and kid. Listing alg_ref in crit means a verifier that doesn't understand it must reject the receipt. Any other header field is rejected.
  • Signing input: protected || "." || payload (the base64url strings), as in JWS.
  • Log line: the canonical JSON of the envelope, one per line. prev in the next receipt is sha256: of that line.
  • Verification order: header checks, then signature, and only then is the payload decoded. Unauthenticated payload bytes are never parsed.
  • Size: about 3,373 bytes of signature per receipt (3,309 ML-DSA-65 + 64 Ed25519). The benchmark reports real storage and latency overhead.
  • Library: Go 1.27 standard library — crypto/mldsa and crypto/ed25519 (verified locally on Go 1.27.1: ML-DSA-65 signs and verifies, 3,309-byte signatures). Warden implements only the composite construction on top, and must pass the draft's test vectors before any receipt is produced (ADR-0006).
  • Test vectors: the draft's Appendix A.1 includes ML-DSA-65-Ed25519 (Figure 4) and ML-DSA-44-Ed25519 (Figure 2). Both are extracted unchanged into testdata/composite/, and internal/composite passes them passing: public keys derived from the seeds, byte-exact M′, and verification of the published signatures.

4.4 Chain and checkpoints (ADR-0003)

  • Genesis: seq=0, prev = SHA-256 of the canonical chain parameters {domain: "agent-warden/genesis/v1", chain_id, alg, alg_ref, kid, key}, where key is the digest of the composite public key that signs the first receipt. The chain is bound to its first signing key; a validly signed first receipt from any other key fails as chain_break. (Binding to the key-epoch certificate follows once certificates are built.)
  • Appending (internal/chain.Appender) passing assigns chain_id, seq, and prev, refuses a timestamp earlier than the previous receipt's, and advances only after a successful signature. The caller must durably write each line before appending the next (ADR-0004).
  • Checkpoint (internal/checkpoint) passing: every N receipts or T seconds (whichever first, with at least one new receipt), Warden signs {v, domain: "agent-warden/checkpoint/v1", chain_id, size, root, head, ts}. root is the RFC 9162 Merkle tree hash over the first size log lines (leaf = SHA-256(0x00 ‖ line), node = SHA-256(0x01 ‖ left ‖ right)); head is the digest of line size − 1. Checkpoints use the same envelope and key as receipts but are not receipts in the chain; their domain keeps the two apart, and tests confirm neither is accepted as the other. The Merkle implementation (internal/merkle) is checked against the transparency-dev test vectors, and its inclusion proofs let a verifier prove one receipt is in the log without the whole log.
  • Anchoring: each signed checkpoint is published outside Warden's control. Implemented: a file anchor that appends one line per checkpoint and syncs every write. It only appends; making the file write-once is the job of where it lives (an append-only filesystem flag, WORM storage, or another account). Reading an anchor verifies every signature and requires strictly growing sizes and non-decreasing timestamps. Not yet implemented: RFC 3161 timestamps and witnesses.
  • Checking a log against checkpoints (chain.VerifyWithCheckpoints): every anchored checkpoint must match the log's prefix of its size. A shorter log means receipts were removed; a different root or head means a rewrite, or an anchor showing a forked history. The report gives Checkpointed (largest size covered) and Unanchored (receipts after it — the exposure window).
  • Exposure window: receipts after the last anchored checkpoint are not truncation-proof (W10 residual risk). Default N=100, T=60s, both configurable.

4.5 Keys

  • Receipt signing keys are held only by the Signer, never by the agent.
  • Each key epoch has an X.509 certificate issued by a Warden root (ADR-0010, internal/identity) passing. Certificates are signed with plain ML-DSA-65 (RFC 9881; ADR-0008), because no mainstream library supports composite X.509. The certificate's subject public key is the ML-DSA-65 component; the Ed25519 component is carried in a SAN URI, urn:warden:ed25519:<base64url>, so the verifier can rebuild the composite receipt key. Purpose is fixed by a certificate policy under Warden's OID arc (…4786.1 key epoch, …4786.2 task credential). A critical extension was the original plan, but Go 1.27 cannot create or parse extensions under the 128-bit UUID OID; a missing Ed25519 key still cannot cause a downgrade, because every receipt needs both signature halves.
  • Task credentials are ML-DSA-65 certificates naming the agent, principal, and task in urn:warden: SAN URIs, valid for at most 15 minutes plus 1 minute of clock skew, with client-authentication key usage.
  • Rotation: a key_rotation receipt signed by the outgoing key names the incoming key; the incoming key signs the next receipt. Verification crosses the boundary.
  • Revocation: receipts under a revoked key dated after the revocation time fail verification; receipts before the last anchored checkpoint still verify.

5. What warden-verify proves

warden-verify --log receipts.jsonl --chain CHAIN_ID --keys trusted-keys.json --anchor anchor.jsonl [--json]
  • --keys is a JWK Set of public keys in the draft's AKP format (kty, alg, kid, pub). This is interim trust input until key-epoch certificates exist (ADR-0008), when it becomes a root certificate. The file is rejected if any key contains private key material, has the wrong algorithm, or repeats a kid.
  • --chain is required, so the log can't choose which chain it claims to be.
  • --anchor is optional but strongly recommended. Without it, the result carries a warning that truncation and full rewrites by the key holder are undetectable.
  • Exit status: 0 verified, 1 verification failed (log or anchor), 2 usage or file error. --json prints the same result for scripts.
  • It builds as a single static binary (CGO_ENABLED=0), about 4 MB. passing

What checkpoints add, tested both ways

Without a checkpoint, truncating the newest receipts and rewriting the whole log with the real key both still verify. Against an anchored checkpoint, truncation below its size, a full rewrite, and an anchor showing a forked history all fail as checkpoint_mismatch.

Changes to receipts after the last checkpoint still verify: that is the exposure window, and the report states its size. Because ML-DSA signatures are randomized, re-signing any receipt changes its bytes, so a rewrite can't reproduce a checkpointed prefix even with the key.

8. Open questions

  1. Policy engine — decided: Cedar (ADR-0007).
  2. Certificate signatures — decided: plain ML-DSA-65 (ADR-0008). The UUID-based OID 2.25.319797216735078154913038669087058524786 is Warden's arc for certificate policies, and the Ed25519 key is bound by SAN URI (ADR-0010).
  3. Draft churn. The composite draft is at -04. If the construction changes, the receipt v and alg must change with it. Is pinning alg_ref in the protected header enough?
  4. SLH-DSA for checkpoints? Hash-based, larger and slower, more conservative — is there a case for using it for checkpoints only, since they are few and long-lived?
  5. Checkpoint anchor for the demo — decided: both (ADR-0014). The timestamp authority is configuration (tsa.url), so a deployment can point at a public one; the demo, tests, and benchmark run a local authority and stay offline. Timestamps are optional and best-effort: they never block a call, and the chain and checkpoints do not depend on them.

Threat modelScope and trust boundaries

Warden's job is to let an AI agent use tools without trusting the model, and to leave behind a record of every action that a third party can verify without trusting Warden's operator. Each threat lists the mitigation and the test that will prove it. Nothing is implemented yet; the tests are the acceptance criteria for the build.

Part A — Enforcement threats

W1Prompt injection through tool output

Threat. A web page, email, or file returned by a tool contains instructions that steer the model's next action.

Mitigation. Policy, not detection, is the guarantee: the model only proposes, and every call is authorized on identity, delegation, and policy. Warden also marks tool output as tainted by source; while tainted content is in context, policy can raise sensitive actions to require approval. Instruction-like content is flagged for the receipt, but detection is heuristic and never the sole control.

Test. Benchmark injection/*: planted instructions; the harmful follow-on call is denied or held, and the receipt records the taint source.

W2Out-of-policy tool call

Threat. The agent calls a tool or argument range the principal is not entitled to.

Mitigation. Deny by default. Policy evaluates principal, agent identity, tool, and arguments (amount limits, recipient domains).

Test. Benchmark authz/*: calls outside the matrix are denied, each with a decision=deny receipt.

W3Credential theft from the agent

Threat. The agent is compromised or talked into printing its environment.

Mitigation. The agent holds no tool credentials. Warden injects them at execution time. The agent holds only a short-lived, task-scoped credential useless without Warden.

Test. Instruct the agent to reveal credentials; assert none exist in its environment or config, and the task credential expires on schedule.

W4Confused deputy

Threat. The agent uses its authority on behalf of someone other than the principal.

Mitigation. Every call is bound to one task and one principal; policy evaluates the principal's entitlements, never the agent's aggregate reach.

Test. Content authored by principal B drives an action in A's task that only B could perform — denied.

W5Tool poisoning and rug pulls

Threat. A tool description instructs the model to do harm, or a tool definition changes after approval.

Mitigation. Manifests are pinned by digest; a changed manifest is refused until re-approved. Every receipt records the manifest digest.

Test. Modify a registered tool's description; calls are refused and receipted.

W6Approval bypass or forged approval

Threat. A high-risk action runs without approval, is self-approved, or reuses an old approval.

Mitigation. Gated calls execute only against an approval receipt naming the exact call digest, a distinct approver, and an expiry. Single-use.

Test. No approval; self-approval; reused approval for a different amount — all refused.

W7Warden bypass

Threat. The agent calls a tool server directly.

Mitigation. Tools accept only Warden-injected credentials; network policy allows tool egress only from Warden.

Test. From the agent's network position, call a tool directly — refused.

W8Fail-open under failure

Threat. Policy, approvals, or the receipt log is down and calls proceed unrecorded.

Mitigation. Fail closed. A call executes only after its decision receipt is durably written.

Test. Make the receipt store read-only; calls are refused, not executed.

Part B — Evidence threats

W9Receipt tampering

Threat. Receipts are edited, inserted, deleted, or reordered to change the story.

Mitigation. Each receipt is signed and carries seq and the previous receipt's hash. Edits break signatures; insertions, deletions, and reorders break the chain.

Test. warden-verify fails and names the first bad seq for a flipped byte, an inserted receipt, a deleted receipt, and a swapped pair.

W10Truncation, rollback, and forked history

Threat. A hash chain alone can't reveal that the newest receipts were cut off, that the key holder rewrote and re-signed the whole log, or that different verifiers were shown different histories.

Mitigation. Signed checkpoints (log size + root hash) sent outside Warden's control — a witness, write-once store, or RFC 3161 timestamp authority.

Test. Truncate after an anchored checkpoint; rewrite and re-sign the whole log with the real key — both fail against the anchored checkpoint.

Residual risk

Receipts written after the last anchored checkpoint can be truncated undetectably. The checkpoint interval is the exposure window — a stated, tunable parameter.

W11Signing key compromise

Threat. An attacker obtains a signing key and forges or rewrites history.

Mitigation. Key lives only in Warden behind a signer interface supporting hardware custody; short epochs; rotation signed by old and new keys; anchored checkpoints bound the damage; revoked-key receipts after revocation are rejected.

Test. Rotate mid-log and verify across the boundary; forge a post-revocation receipt with a revoked key — rejected.

W12Harvest now, forge later

Threat. Receipts must stay trustworthy for years; a future quantum computer could forge classical signatures, making an Ed25519-only log deniable.

Mitigation. Hybrid ML-DSA-65 + Ed25519 composite signatures — unforgeable as long as either component holds.

Test. Verification fails if either component is altered or stripped (no downgrade).

W13Sensitive data leaking into receipts

Threat. Receipts are shared with verifiers, but arguments and results contain personal or confidential data.

Mitigation. Receipts hold salted commitments, never raw values; raw data and salts are stored separately and disclosed selectively.

Test. Scan all benchmark receipts for seeded synthetic PII and secrets — none; a selectively disclosed call verifies against its commitment.

W14Replay across contexts

Threat. A valid receipt or approval from one chain, task, or deployment is presented in another.

Mitigation. Every signed payload includes chain ID, task ID, and a domain-separation label; the composite scheme adds its own algorithm label.

Test. Splice a receipt from chain A into chain B — rejected.

Out of scope (documented, not hidden)

  • A compromised Warden host at signing time. Warden will faithfully sign what a compromised Warden tells it to. Confidential computing and remote attestation of Warden are future work.
  • Proving the tool actually did what it reported. Receipts prove what Warden authorized, sent, and received.
  • Prompt-injection detection accuracy. Heuristics are reported honestly, including false positives; policy is the control.
  • Model-level jailbreak research. Warden constrains actions, not model outputs.
  • Cross-organization key federation.

DecisionsArchitecture decision records

ADR-0001 — A self-contained gateway, receipt log, and benchmark Accepted

Decision. One self-contained repository with (1) the gateway — identity, policy, approvals, credential brokering, tool pinning, output inspection; (2) the receipt library and warden-verify, with no dependency on the gateway; (3) a demo agent and synthetic tools so everything runs with no infrastructure beyond a model endpoint. Identity is deliberately minimal: a small internal CA issuing short-lived, task-scoped X.509 credentials.

Why. Warden must show prevention, verifiable evidence, and measurable results — each needs a different piece, and all must be reproducible on a laptop.

Rejected. Receipt library only (can't show enforcement or run the benchmark); gateway with conventional logging (loses the main contribution); a full identity stack (heavy setup obscures the core ideas).

ADR-0002 — Hybrid composite ML-DSA-65 + Ed25519 signatures Proposed

Decision. Sign receipts with composite ML-DSA-65-Ed25519 per draft-ietf-jose-pq-composite-sigs-04 in a JWS envelope, pinning the draft revision in the protected header (alg_ref). Build on the Go standard library's ML-DSA-65 and Ed25519 primitives, implement only the composite construction, gate it on the draft's test vectors. Both components required; no single-component fallback.

Why. Receipts are long-lived evidence (W12). ML-DSA is standardized (FIPS 204; JOSE/COSE encoding published as RFC 9964) but young; a hybrid holds if either algorithm breaks.

Consequences. ~3.4 KB per receipt. If the draft changes, bump the receipt version; old receipts stay verifiable under their pinned alg_ref. ML-DSA-65 alone (RFC 9964) is the fallback as a new version, never a silent downgrade.

Rejected. Ed25519 only; ML-DSA-65 only; unbound dual signatures; SLH-DSA per receipt (too large/slow; still considered for checkpoints); HMAC logs (only secret holders can verify, and any can forge).

ADR-0003 — Hash chain, signed checkpoints, external anchoring Proposed

Decision. Chain receipts with seq + prev; every N receipts or T seconds sign a checkpoint {chain_id, size, root} over a Merkle tree; anchor each checkpoint outside Warden's control (write-once file or RFC 3161 in v1); verify against the most recent anchor and report the exposure window.

Why. Per-receipt signatures prove authenticity, not completeness. A chain alone misses truncation, full rewrites by the key holder, and forks.

Consequences. Tampering before the last anchor is detectable even with the key. The window after it (default 100 receipts / 60 s) is named, not hidden. Anchor outages degrade evidence strength but don't stop tool calls.

Rejected. Chain only; a public transparency log per receipt (leaks metadata, adds latency — possible future target for checkpoints); blockchain anchoring.

ADR-0004 — Fail closed with write-ahead receipts Proposed

Decision. No receipt, no action. A call runs only after its decision receipt is durably written; on write failure the call is refused. A missing result receipt after execution is detectable and alerts.

Why. Best-effort audit pipelines drop events exactly when something is already going wrong.

Consequences. Receipt storage is on the availability path — an outage stops tool use, intentionally. Signing and fsync add per-call latency, measured in the benchmark.

Rejected. Async best-effort logging; writing only after execution (a crash leaves no record).

ADR-0005 — Commitments, not raw data, in receipts Proposed

Decision. commitment = SHA-256(salt ‖ JCS(value)) with a fresh 32-byte salt per value. Raw values and salts are stored separately under access control and disclosed selectively.

Why. Receipts are meant to be shared; raw data would make every verifier a data recipient, and plain redaction can't prove what a call contained.

Consequences. Share receipts widely; prove one call without revealing others; delete value + salt for retention obligations and the receipt still verifies. The separate data store becomes a new asset to protect.

Rejected. Raw values; unsalted hashes (brute-forceable); HMAC (reintroduces a shared secret); encrypting values inside receipts.

ADR-0006 — Go for the trust path, Python for the demo and benchmark Accepted

Decision. Go 1.27 for the receipt library, composite signer, chain and checkpoints, warden-verify, and the gateway. Python 3.13+ for the demo agent, synthetic tools, and benchmark. The two sides interact only through MCP and the language-neutral receipt format. Prefer Go's standard library for all cryptography.

Why. The trust path needs correctness, few dependencies, low latency, and a verifier auditors can run without an environment. The demo and benchmark need speed of development and the agent ecosystem. Go 1.27 now has ML-DSA and ML-DSA X.509 in the standard library (verified locally); neither Go nor Python implements composite signatures.

Consequences. warden-verify ships as a single static binary (requires pure-Go SQLite). Compiler-checked crypto code; a FIPS 140-3 mode is available (crypto/mldsa needs Go Cryptographic Module v1.26.0+). Two toolchains, slower prototyping, and cross-language tests are required.

Rejected. All Python (verifier needs an environment, weaker gateway latency, more trust-path dependencies); all Go (demo and benchmark far from the agent ecosystem); Rust for the trust path (less mature ML-DSA and MCP ecosystem, steeper build).

ADR-0007 — Cedar for tool-call authorization Accepted

Decision. Embed Cedar via cedar-go. Entities: principal, agent, tool, task; context: validated arguments, taint sources, approval state. Default deny, forbid overrides permit. Because Cedar returns only allow/deny, Warden evaluates two actions: call denied → deny; call_unattended allowed → allow; otherwise require_approval. Receipts record the policy set digest and determining policy IDs.

Why. Authorization-specific language that is easier to audit; forbid-wins semantics express limits that must never be overridden.

Consequences. The two-action pattern needs explicit tests. Which schema-validation and analysis features cedar-go supports must be checked before Phase 2. Complex data joins must be computed by the gateway before evaluation.

Rejected. OPA/Rego (more flexible than needed, harder to audit); hand-written Go rules (policy changes become code changes).

ADR-0008 — Plain ML-DSA-65 certificates; receipts stay hybrid Accepted Superseded in part by ADR-0010

Decision. All certificate signatures use plain ML-DSA-65 (RFC 9881). Key-epoch certificates carry the ML-DSA-65 component as the subject public key and bind the Ed25519 component in a critical Warden extension; the verifier rebuilds the composite key and rejects certificates without it. The extension OID is the UUID-based 2.25.319797216735078154913038669087058524786 (ITU-T X.667), generated once and never to be regenerated.

Why. Composite X.509 is unsupported in Go 1.27, pyca cryptography 50.0.1, and OpenSSL 3.6.4; plain ML-DSA-65 certificates are supported and verified locally.

Consequences. Standard formats throughout. No classical hedge on the chain — limited by short-lived internal certificates, anchored checkpoints, and hybrid receipts. Generic tools will reject the unknown critical extension unless told to ignore it.

Rejected. Hand-built composite certificates; parallel ML-DSA-65 + Ed25519 certificates; a JSON key manifest instead of X.509; a non-critical extension (allows silent downgrade).

ADR-0009 — Approval receipts Accepted

Decision. An approval receipt carries the decision's task, actor, and call, plus {decision_seq, outcome, approver, statement, expires_ts}. statement is the digest of a statement the approver signs with their own key, covering the exact call they were shown; Warden verifies it before writing the receipt and stores the full statement separately. Demo approvals use warden approve <decision_seq> (or --reject).

Rules checked by warden-verify. The approval must match an earlier require_approval decision; one approval per decision; the approver differs from the principal; a result needs an earlier approved outcome and must not be after expires_ts. New reasons: duplicate_approval, self_approval, rejected_call_executed, approval_expired.

Consequences. missing_approval becomes a real check. Approver keys are a second trust list. Expiry relies on Warden-written timestamps, bounded by anchored checkpoints.

Rejected. Warden-only approvals (only as trustworthy as Warden); approver signing the receipt itself (two signers in the chain); a web approval queue (UI work unrelated to the security claims).

ADR-0010 — Identity and certificate profile Accepted

Context. Go 1.27 stores extension and extended-key-usage OIDs as []int, so it cannot create a certificate extension under the 128-bit UUID OID, and ParseCertificate rejects any certificate carrying one. The same OID works fully as a certificate policy.

Decision. The OID becomes Warden's arc: .1 marks key-epoch certificates, .2 task credentials, each as exactly one certificate policy. The Ed25519 key moves to a SAN URI, urn:warden:ed25519:<base64url>. Task credentials carry urn:warden:agent, principal, and task URIs, client-auth key usage, and at most 15 minutes of validity. Identity is read only from urn:warden: URIs, each exactly once; unknown Warden URIs and DNS, email, or IP names are rejected.

Consequences. Every certificate is standard X.509. Dropping the critical flag does not allow a downgrade, because receipts need both signature halves. A task credential cannot pass as a key-epoch certificate, or the reverse. Revocation is still deferred.

Rejected. An IANA Private Enterprise Number (waits on registration); hand-encoded certificates (reimplements X.509 parsing and validation).

ADR-0011 — MCP transport and agent authentication Accepted

Decision. Agents reach Warden over stateless MCP Streamable HTTP on TLS 1.3 with mutual authentication; the client certificate is the agent's task credential, so the handshake proves the agent holds its key. A middleware overwrites any client-supplied X-Warden-Peer-Certificate header with the verified certificate, and the gateway verifies it again. Warden's own server certificate is a third profile (policy …4786.3) that agents check. Pinned tools are exposed as server.tool, plus warden.resume. Upstream HTTP servers get header credentials per call; stdio servers get server-wide environment credentials at start, with only PATH from Warden's environment.

Why. Probed: Go 1.27 completes mutual TLS 1.3 with ML-DSA-65 certificates; the MCP SDK's stateless mode gives each request its own TLS identity, where sessions could be reused by another client.

Consequences. No bearer tokens for agents. No server-to-client requests (sampling, elicitation). Agents reconnect when their credential expires. Tools are listed upstream on every call, adding latency.

Rejected. Certificates sent as data (replayable); OAuth bearer tokens (stealable); stdio between agent and Warden (puts Warden inside the agent's trust boundary); stateful sessions (reusable by another client).
